Pendências declaradas (o que a marcação pura não resolve):

  • Foco automático no primeiro erro de validação: Com o uso de novalidate e do script padrão do Bootstrap, o foco do teclado permanece no botão de submissão ("Fazer pedido") em caso de falha, exigindo script personalizado para redirecionar o foco ao primeiro campo inválido.
  • Modal dinâmico por produto: Apenas o açaí possui diálogo estruturado na marcação estática; exibir os detalhes dinamicamente para os demais 6 produtos sem duplicar marcação exigirá integração via JavaScript ou renderização por componentes no Bloco 2.

2. O registro de decisão

Contexto

A AgroFeira necessita de uma estratégia de estilização sustentável para a transição do catálogo estático para uma aplicação dinâmica em React no Bloco 2. Na Atividade 5, a folha autoral entregou apenas 2,1 kB de CSS e LCP de 41 ms (39,4 kB transferidos totais), enquanto o Bootstrap exigiu 33,4 kB transferidos de CSS (232 kB descomprimidos) e LCP de 98 ms (108 kB totais). Na Aula 6, a introdução do script do Bootstrap adicionou mais 25,2 kB transferidos (80,5 kB descompactados), e a desativação do JavaScript causou a quebra total da navegação mobile e da validação no checkout, onde o formulário submeteu dados vazios sem restrição.

Opções consideradas

  • Folha autoral (CSS Moderno com @layer e Tokens): Ganha controle total de bytes, zero dependência externa e resiliência com JS desativado; cobra maior esforço manual para construir comportamentos interativos complexos acessíveis.
  • Bootstrap 5.3: Ganha prototipação acelerada de componentes comuns (navbar, modal); cobra 312,5 kB de recursos descompactados (CSS + JS) e conflita conceitualmente com a manipulação do DOM virtual pelo React.
  • Tailwind CSS (Utility-First): Conforme os slides da Aula 6 ("Outra abordagem: utilitários", p. 106), elimina CSS não utilizado na compilação final e evita nomes de classes arbitrários, mas exige utilitários extensos no JSX e compilação em build time.

Decisão

Decidimos adotar a Folha Autoral com CSS Moderno e Design Tokens para as próximas fases do projeto, integrando utilitários modulares apenas onde estritamente necessário.

Consequências aceitas

  • Necessidade de implementar e testar manualmente comportamentos interativos acessíveis (como armadilhas de foco em modais e menus colapsáveis) quando integrados ao ecossistema de componentes do React.
  • Tempo adicional de desenvolvimento na criação de novos padrões de tela (como tabelas administrativas responsivas), dispensando o ganho de velocidade imediato das classes prontas do Bootstrap.

O que me faria mudar de ideia

A expansão imediata do escopo da AgroFeira para um painel administrativo denso com dezenas de formulários e dashboards complexos, ou a constatação de que a equipe não consegue manter a consistência dos tokens de acessibilidade sem o rigor padronizado de um framework consolidado.
